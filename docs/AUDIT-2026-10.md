# App audit — October 2026

Scope: UI structure and consistency, database structure for multiple households, legacy and unused code.

## Status (done on this branch)

Decisions: the catalogue is edited only by named admins (`app_admins`, seeded with the first household's creator), and each person belongs to one household.

- **Backend**: B1–B9, B11–B13 done (`20261112000001_households.sql`, `tests/households_isolation_test.sql`). Also fixed: `put_grocery_item` failed on a new name. Not done: B10 (the prompt scheduler is fine at this size) and B14 (locale and colour columns; no user-visible effect).
- **UI**: U1–U9 done. Inline styles remain only for computed values (member colours, drag position, fill widths).
- **Legacy**: L1–L10 done, except that `copy_recipe` and the `recipe_source` values `photo` / `ai` stay. `copy_recipe` is the copy-on-write that recipe editing will use. Removing enum values means rebuilding the type, and import from photos and AI is still planned. L11 (squashing the migrations) and L12 (exports used only in their own file) are left for later.

The findings below are as written before the work. Severity: **P0** = fix before a second household signs up, **P1** = should fix, **P2** = clean-up.

## 1. Backend: data segmentation for multiple households

### How it works today

The model is already "central + own", and that's the right base:

| Layer | Tables | Who sees it |
| --- | --- | --- |
| Central (`household_id is null`) | `recipes` (seed library), `products` (shared catalogue), `tag_catalog` (shared tags) | everyone |
| Central, fully global | `ingredient_catalog`, `ai_cache` | everyone (`ai_cache` server only) |
| Household | `households`, `household_members`, `invites`, `recipes`/`products`/`tag_catalog` with a household id, `household_products` (overlay on central products), `household_stores`, `household_staples`, `household_aisle_order`, `plan_days`, `meals`, `decks` + children, `grocery_items`, `grocery_add_batches` | members only (`is_member()`) |
| Private to one person | `member_goals`, `taste_rules`, `learned_patterns`, `push_subscriptions`, `grocery_presence`, `member_portions` | that person only |

RLS is on for every table, security-definer functions pin `search_path`, and the edge functions filter on the caller's household. Overriding central data works in two ways: copy-on-write for recipes (`copied_from` + `library_recipes`) and an overlay row for products (`household_products`).

### Findings

| # | Sev | Finding | Where |
| --- | --- | --- | --- |
| B1 | **P0** | **Any household owner can edit the central catalogue.** `is_catalog_admin()` is "owns *a* household", so as soon as there's a second household, its creator can rewrite the shared products for everyone. The "Edit the catalog" entry is shown on the same rule. | `20261103000001_groceries_v2.sql:129-140`, `Us.tsx` (`owner_id === userId`), `Catalog.tsx` |
| B2 | **P0** | **Foreign keys cross households.** FKs skip RLS, so a member can write a row in their own household that points at another household's private row: `grocery_items.product_id / store_id / recipe_id`, `meals.recipe_id`, `plan_days.recipe_id`, `household_products.product_id`, `taste_rules.product_id`. The RPCs check this, but the policies on direct table writes (`grocery_all`, `meals_all`, `plan_days_all`, `household_products_all`) don't. Security-definer code then reads the foreign row, e.g. `enqueue_grocery_pushes` reads `products.name_en` for the push text. | `20261027000003_rls.sql:156-165`, `20261030000002_grocery_products.sql:86-89` |
| B3 | P1 | `put_grocery_item` returns success when the id exists **in any household** (`where id = p_id`, no household filter). That makes it an existence oracle, and an id collision is silently accepted. | `20261103000001_groceries_v2.sql:231` |

| B5 | P1 | **One household per user is hard-wired**: a unique index on `household_members(user_id)`, and every RPC infers the household with `my_household_id()`. | B6 | P1 | **Muting "New deck" notifications does nothing.** `deal-deck` inserts `deck_dealt` straight into `push_outbox` and skips `enqueue_push()`, the one place that applies `push_enabled` / `push_muted`. | `functions/deal-deck/index.ts` (end), `Notifications.tsx:16` |

| B9 | P2 | `catalog_version()` fingerprints products and ingredients but not `tag_catalog`, so tags use a different caching system (see U5). | `20261102000001_catalog_version.sql` |

| B11 | P2 | `grocery_items` keeps cleared rows forever (they feed usuals and "probably at home"). It needs a retention rule per household, e.g. 12 months. | `schema.sql` |
| B12 | P2 | No test checks isolation between two households across all tables. The tests only cover "outsider without a household", tags and products. | `supabase/tests/` |
| B13 | P2 | Two server systems add list lines: `add_grocery_items` (merges, server ids) and `put_grocery_item` (client ids, never merges). They duplicate the product resolution, overlay and `household_products` bookkeeping. | groceries migrations |
| B14 | P2 | `profiles.locale` allows only `en`/`fr`, while recipes carry `it`. `profiles.color` defaults to a hard-coded hex instead of a member-colour index. | `schema.sql` |

### Action plan (backend)

1. **Platform admin (B1)**: new table `app_admins(user_id pk)`, with no client policies. `is_catalog_admin()` becomes `exists (select 1 from app_admins where user_id = auth.uid())`. Seed yourself into it, and gate the Catalog entry in Us on an RPC `is_catalog_admin()` instead of `owner_id`. Add a test: household B's owner cannot update a shared product.
2. **Same-household references (B2, B4)**: one trigger function `assert_same_household()` on `grocery_items`, `meals`, `plan_days`, `household_products` and `taste_rules`. It rejects a referenced product, recipe or store that is neither central nor the row's own household. For stores, a composite FK `(household_id, store_id) → household_stores(household_id, id)` is enough. Add `check (household_id is null or ingredient is null)` on `products`.
3. **`put_grocery_item` (B3)**: filter the existence check on `household_id = v_household`, and raise `id_taken` otherwise.
4. **Decide B5.** If one household per user stays the rule, document it in SETUP.md and keep it. If not, add `profiles.current_household_id`, make `my_household_id()` read it, and drop the unique index.
5. **Notifications (B6)**: `deal-deck` calls `rpc('enqueue_push', …)` through the service client instead of inserting into the outbox directly.
6. **Owner (B7)**: keep `household_members.role` as the only source of truth. Make `owner_id` a view/derived value or drop it, and change `is_owner()` and `households_delete`.
7. **RLS performance (B8)**: rewrite the household policies as `household_id = (select public.my_household_id())`, in one migration with tests.
8. **Isolation test suite (B12)**: two households, A and B. For every table, B selects, inserts, updates and deletes A's rows and gets nothing or an error; also check that A sees the central rows. Run it in CI.
9. Later: tags in `catalog_version()` (B9), list retention (B11), merge the two add paths behind one function (B13), and locale/colour (B14).

## 2. UI: structure and consistency

### What's good

There's one token file (generated from `design/tokens.json`), a single `app.css` with BEM-like blocks, a small primitives file (`components/ui.tsx`: Button, Chip, Segmented, Checkbox, Switch, Avatar, Screen, Field, Stepper, Sheet, Toast, Spinner), all strings in i18n, and almost no hex colours in TSX.

### Action plan (UI)

1. **Add the missing primitives to `ui.tsx`**:
   - `ListRow` (props `icon`, `title`, `meta`, `to | onClick`, `trailing`, `chevron`; always reserves the icon column when the list has any icon);
   - `Section` (`label`, `hint`, children; replaces `section-label` + hint `<p>`);
   - `SheetHeader` (`title`, `subtitle`);
   - `ProgressBar`;
   - `SearchField` (leading icon, clear, Enter-to-pick);
   - `Button variant="danger"`;
   - `ConfirmSheet` (or a promise-based `confirm()` built on `Sheet`).

   Then migrate screen by screen. This alone removes most inline styles (U1, U3, U4, U7).
2. **Spacing utilities**: add the few modifiers the inline styles imitate (`.mt-3`, `.mt-6`, `.flush`, or better, give `Section`/`SheetHeader` their own margins). Ban `style={{` for spacing with an oxlint rule or a review rule. Move the `#fff`/`rgba` values into tokens.
3. **One product search (U2)**: a `useProductSearch(catalog, query, rank?)` hook plus a `ProductResults` list with an optional per-row trailing slot. Groceries, ProductPicker, Tastes and Catalog use it. Recipes uses the same `SearchField`.
4. **One destructive pattern (U4)**: undo toast where the action can be reversed (list lines, tags, staples), `ConfirmSheet` where it can't (leave household, delete recipe, remove member).
5. **One data pattern (U5)**: every read goes through `useLive` (with `tables: []` when it doesn't need realtime). Every write goes through a small `mutate(promise, {success?, error})` helper that toasts errors. Fold tags into `cachedCatalogue` once `catalog_version()` includes them (B9).
6. **One add-to-list path (U6)**: `AddToListSheet` enqueues `put` ops in `listQueue` (merge on the client, as Groceries does), or `listQueue` grows an `addMany` op backed by `add_grocery_items`. Pick one and delete the other.
7. **IA (U8)**: Us = You (goals, tastes, notifications, profile & appearance, language) + Household (members, plan, settings, catalog if admin). One `MemberList` component. Routes under `/us/...`.
